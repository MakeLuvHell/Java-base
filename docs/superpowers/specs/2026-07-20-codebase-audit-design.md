# RuoYi-Vue 代码库审计文档设计

## 目标

为接手 RuoYi-Vue 的开发与安全维护人员建立一套可持续维护的中文审计文档。文档需要帮助读者快速理解系统结构、前端 UI 与配色体系、安全边界和整改优先级，并让每项重要结论都能追溯到代码或验证结果。

本轮只审计并落盘文档，不修改业务代码。后续是否实施整改由用户依据审计结果另行决定。

## 当前基线

- 项目版本：RuoYi 3.9.2。
- 后端：Java 17、Spring Boot 4，多模块 Maven 工程。
- 前端：Vue 2、Vue Router 3、Vuex、Element UI、Vue CLI。
- 身份与权限：Spring Security、JWT、Redis、动态菜单与方法级权限。
- 当前仓库没有 `CONTEXT.md`、`CONTEXT-MAP.md`、`docs/adr/` 或 `knowledge/`。

这些信息仅用于确定审计入口。正式报告中的版本、边界和行为仍需通过代码与构建结果逐项核实。

## 文档结构

审计结果采用专题文档集：

```text
CONTEXT.md
docs/audit/
├── README.md
├── 01-architecture.md
├── 02-frontend-ui.md
├── 03-security.md
└── 04-remediation-roadmap.md
```

各文件职责如下：

- `CONTEXT.md`：只收录稳定的项目术语、模块名称和系统边界，不存放实现细节、临时审计笔记或整改方案。
- `docs/audit/README.md`：说明审计基线、范围、方法、限制和核心结论，并提供专题导航。
- `docs/audit/01-architecture.md`：记录模块职责、依赖关系、启动链路、请求链路、认证与动态菜单链路、主要存储及部署边界。
- `docs/audit/02-frontend-ui.md`：记录页面信息架构、布局与组件体系、实际颜色令牌及用途、状态反馈、主题能力、响应式和可访问性观察。
- `docs/audit/03-security.md`：维护风险台账，并详细分析身份认证、授权、输入与输出、文件处理、数据访问、运维端点、日志与配置、供应链等安全面。
- `docs/audit/04-remediation-roadmap.md`：将发现项按 P0 至 P3 排序，关联影响文件、建议顺序、兼容影响和可执行的回归验证。

当前没有需要记录的不可逆架构决策，因此不创建 ADR。若审计后续产生真实、难以逆转且存在明确权衡的整改决策，再单独提议 ADR。

## 审计方法

### 架构与数据流

从应用启动入口和配置文件开始，沿 Controller、Spring Security、Service、Mapper、Redis 与数据库追踪核心链路。至少覆盖：

- 登录、验证码、JWT 签发、续期和退出登录。
- 已认证请求进入安全过滤器、获取用户上下文和完成方法级授权。
- 后端菜单数据生成前端动态路由与按钮权限。
- 数据权限注入、MyBatis 映射和分页。
- 文件上传、下载、静态资源映射和富文本内容。
- 定时任务、代码生成器和监控端点。

正式文档用 Mermaid 图和表格表达多模块依赖及跨层链路；文字说明负责约束条件和例外情况。

### 前端 UI 与配色

UI 结论以现有实现为准，从全局 SCSS、Element UI 变量覆盖、布局组件、主题设置和代表性页面提取。报告至少记录：

- 登录页、主框架、侧边栏、顶栏、页签、内容区和典型 CRUD 页面的结构。
- 全局样式、组件级样式与 Element UI 覆盖之间的优先级关系。
- 主色、中性色、背景色、边框色、文字色和成功、警告、危险、信息状态色的实际值与用途。
- 布局尺寸、间距、字号、圆角、阴影和交互状态。
- 暗色或主题切换的实际覆盖范围。
- 键盘操作、焦点可见性、对比度、语义标签、响应式适配和内容溢出方面的缺口。

本轮描述并评估现有设计，不提出一套脱离代码的新视觉方案。

### 安全

安全审计至少覆盖：

- 认证、密码规则、验证码、登录限制、JWT 密钥与令牌生命周期。
- URL、方法、按钮和数据级权限的一致性。
- SQL 注入、表达式或反射调用、反序列化、XSS、开放重定向、SSRF、CSRF 和 CORS。
- 文件名、扩展名、MIME、大小、路径穿越、下载与静态资源暴露。
- Druid、Swagger/OpenAPI、监控、缓存、定时任务和代码生成器暴露面。
- 数据库、Redis、日志、异常响应、敏感字段和默认配置。
- Maven 与 npm 依赖版本、构建配置和可执行的供应链检查。

每个发现项包含唯一编号、严重度、可信度、状态、影响、触发条件、证据、整改建议和验证方法。结论分类如下：

- 已确认问题：代码行为或可复现检查足以证明问题存在。
- 条件性风险：仅在特定部署或配置条件下成立，并明确列出这些条件。
- 设计观察：当前不构成可利用漏洞，但会增加维护或防御成本。
- 未能动态验证：受本地服务、数据或工具条件限制，不能做出确定结论。

严重度使用 P0 至 P3：P0 表示可导致系统级紧急损害，P1 表示高影响且应优先修复，P2 表示中等风险或纵深防御缺口，P3 表示低风险与维护性改进。严重度与整改路线中的排序必须一致。

### 可执行验证

在不修改业务代码的前提下执行仓库已有测试和构建，并运行环境允许的依赖与静态检查。预期至少包括：

- Maven 测试或打包验证。
- 前端依赖状态与生产构建验证。
- 敏感信息、危险 API、未受控动态 SQL、宽泛匿名访问和上传处理模式的定向检索。
- 可用时执行 Maven 与 npm 依赖安全审计。

无法执行或结果受网络、外部数据库、Redis、Node/JDK 版本影响的检查，必须在审计范围限制中明确记录，不以推测代替结果。

## 证据与引用规则

- 本地代码证据使用仓库相对路径和准确行号。
- 对跨文件链路同时引用入口、关键转换点和最终敏感操作。
- 引用配置时描述配置键和安全影响，不复制密码、密钥或令牌值。
- 外部漏洞信息必须注明来源、受影响版本条件和本项目是否实际引入对应组件。
- 自动扫描结果必须人工核对可达性和配置条件，避免直接把工具告警等同于漏洞。
- 文档内部使用相对链接，并保持风险编号在安全报告与整改路线中一致。

## 验收标准

审计文档完成时应满足：

1. 新接手的开发人员能从总览定位各后端模块、前端边界和主要运行链路。
2. UI 文档包含从代码提取的颜色值、布局规则和组件关系，并明确可访问性与响应式缺口。
3. 每项重要安全结论都有可定位的代码证据、明确的成立条件和可执行验证方法。
4. 风险严重度、状态和整改顺序在所有文档中保持一致。
5. 文档相互链接有效，不含未解释缩写、占位符或未经标注的推测。
6. 记录实际执行的构建与检查命令、结果和限制。
7. 工作树除审计、上下文和规划文档外，不包含业务代码变更。

## 非目标

- 不修复审计中发现的问题。
- 不重构模块或升级依赖。
- 不重新设计或实现前端界面。
- 不对未启动的生产环境进行渗透测试。
- 不创建缺乏真实决策背景的 ADR。
