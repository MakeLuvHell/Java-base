# 可观测性与运维指南

本文定义如何判断系统是否健康、如何定位问题、何时告警，以及事件发生后如何记录和恢复。

> **当前基线（2026-08-03）：** 系统已有操作日志、登录日志、在线用户、定时任务日志，以及服务、缓存和 Druid 管理页面；这些能力分散且偏管理台查看。
> **目标状态：** W12 补齐统一 request ID、liveness / readiness、结构化日志、指标、告警、看板与可执行 runbook。
> **安全边界：** Swagger、Druid、指标和管理端点不能因排障需要而默认暴露到公网。

相关：[发布与回滚](./deployment-and-rollback.md) · [安全审计](../audit/03-security.md) · [W12 任务书](../intern/tasks/W12-deployment-production-readiness.md)

## 1. 观测目标

值守人员应能在几分钟内回答：

1. 用户现在能否访问系统并完成核心操作？
2. 问题从什么时候开始、影响哪些用户 / 接口 / 环境？
3. 故障位于入口、应用、MySQL、Redis、任务还是文件存储？
4. 最近是否有发布、迁移、配置或流量变化？
5. 需要继续观察、降级、回滚还是升级为安全事件？

单一日志或“服务监控”页面不能回答全部问题，需组合日志、指标、健康检查、追踪上下文和业务事件。

## 2. 当前能力与缺口

| 信号 | 当前能力 | 目标补充 |
| --- | --- | --- |
| 审计日志 | 操作日志、登录日志 | 统一事件字段、保留策略、敏感信息抽查 |
| 会话 / 任务 | 在线用户、任务执行日志 | 有界查询、失败率 / 延迟指标和告警 |
| 资源 | 服务监控、缓存监控、Druid | 时序指标、趋势看板、受控端点 |
| 请求链路 | 普通 Web / 应用日志 | request ID 从 Nginx 到后端并返回客户端 |
| 健康 | 尚无仓库级 liveness / readiness 契约 | 区分进程存活与接流量能力 |
| 告警 | 尚无统一规则和事件流程 | 分级、去重、负责人、升级和恢复记录 |
| 业务指标 | 内置功能日志为主 | 工单等新领域的成功 / 失败 / 积压指标 |

“目标补充”在对应实现合入前不能作为当前能力对外承诺。

## 3. 信号模型

### 3.1 四类信号

| 类型 | 回答的问题 | 示例 |
| --- | --- | --- |
| 日志 | 某次事件具体发生了什么 | 请求错误、登录失败、任务异常 |
| 指标 | 一段时间内趋势和规模如何 | 请求率、错误率、P95、连接池使用率 |
| 健康检查 | 实例能否存活 / 接流量 | liveness、readiness |
| 业务 / 审计事件 | 谁在何时对什么做了什么 | 权限变更、工单流转、附件删除 |

当前单体架构不强制引入完整分布式追踪平台，但 request ID 和稳定业务标识必须让日志可关联。

### 3.2 共同维度

日志和指标标签至少考虑：

- `environment`、`service`、`version` / commit。
- HTTP method、规范化 route、status class。
- request ID；有登录态时使用内部 user ID，避免用户名 / 手机号作标签。
- 任务名、业务动作、结果；业务对象 ID 只进日志，不做高基数指标标签。

禁止把完整 URL 查询串、Token、文件路径或任意用户输入直接当指标标签。

## 4. Request ID 约定

目标链路：

```text
Browser / caller
  → Nginx 接受合法 X-Request-ID 或生成新值
  → backend filter 校验 / 生成并写入 MDC
  → Controller / Service 日志自动带 requestId
  → response header 返回 X-Request-ID
```

实现要求：

- 只接受规定长度和字符集的外部 ID；非法值替换，防止日志注入。
- 一个请求内保持不变；异步任务显式复制上下文或创建新的关联 ID。
- Nginx access log 与后端日志使用同一个字段名或可明确映射。
- 错误响应向客户端返回 request ID，方便支持人员检索。
- request ID 不是认证凭据，不能据此授权或访问其他请求数据。

验证时发起一条成功请求和一条 4xx / 5xx 请求，确认入口、后端和响应头可以串联。

## 5. 日志规范

### 5.1 建议字段

| 字段 | 说明 |
| --- | --- |
| timestamp / level | 含时区的时间、稳定日志级别 |
| service / environment / version | 哪个服务、环境和版本 |
| requestId | 请求关联标识 |
| logger / event | 代码来源与稳定事件名 |
| method / route / status / durationMs | 规范化 HTTP 结果 |
| userId / businessId | 必要时记录内部 ID，不记录完整个人信息 |
| errorType / message | 可行动的错误类别和脱敏摘要 |

日志格式可以先保持现有文本，但字段语义必须稳定；接入集中检索时再评审 JSON 结构化输出。

### 5.2 级别

- `ERROR`：请求或后台任务失败，需要处理或统计。
- `WARN`：可恢复异常、降级、重试、权限拒绝异常升高等。
- `INFO`：启动、停止、发布版本、关键业务 / 运维事件。
- `DEBUG`：仅开发 / 短时诊断，生产默认关闭且有到期时间。

预期的参数校验失败不应全部打印堆栈；未知异常必须保留内部错误类型和 request ID，但响应不能泄露堆栈。

### 5.3 禁止记录

- 密码、JWT、Authorization / Cookie、验证码、secret 和数据库口令。
- 完整身份证号、手机号、邮箱、真实姓名等非必要个人数据。
- 完整请求 / 响应体，尤其登录、上传和富文本内容。
- 受保护附件的物理绝对路径、签名 URL 和文件内容。
- 带敏感查询参数的完整 URL。

确需定位时采用字段白名单、掩码、采样和限时开关。日志本身要有访问控制、保留周期、轮转和磁盘上限。

## 6. 健康检查

### 6.1 Liveness

只回答“应用进程是否还能工作”。不应因为 MySQL / Redis 短时抖动就反复重启所有实例，从而放大故障。

### 6.2 Readiness

回答“应用现在能否安全接收业务流量”，至少考虑：

- 应用启动已完成。
- 所需数据库迁移已成功。
- MySQL 可执行轻量查询。
- Redis 可用性符合登录态依赖要求。
- 必需目录可访问；若上传不可用会影响核心业务，应反映为未就绪或明确降级。

### 6.3 端点安全

- 对外只返回最少状态，不泄露数据库地址、环境变量、beans 或完整异常。
- 详细健康和指标仅管理网络或授权身份可达。
- Nginx、容器编排和发布脚本使用稳定端点，不用业务列表接口冒充健康检查。
- 每个检查有严格超时，避免依赖卡住拖垮健康线程。

## 7. 指标设计

### 7.1 请求黄金信号

- 请求率：按 route / method 聚合。
- 错误率：区分 4xx、5xx；权限拒绝与系统错误分开。
- 延迟：P50 / P95 / P99，避免只看平均值。
- 饱和度：线程池、连接池、CPU、内存和队列使用情况。

### 7.2 运行时与依赖

- JVM heap / non-heap、GC 次数与暂停、线程、进程 CPU。
- Druid 活跃 / 空闲 / 等待连接及获取连接耗时。
- Redis 命令错误、超时、连接和内存；禁止用生产 `KEYS *` 做监控。
- 磁盘、日志目录和上传卷容量 / inode。
- 定时任务成功 / 失败 / 耗时，连续失败和积压。

### 7.3 业务指标

新工单领域落地后再增加：

- 创建、受理、解决、关闭的成功 / 失败数。
- 各状态工单数量与超时积压。
- 状态冲突 / 幂等重复请求数。
- 通知发送失败 / 重试 / 死信。
- 附件写入失败、元数据不一致和清理失败。

指标不能包含用户名、标题、附件名、ticket ID 等高基数或敏感标签。

## 8. 看板

至少按三层组织，不把所有图塞进一个页面：

| 看板 | 主要内容 | 使用者 |
| --- | --- | --- |
| 服务总览 | 流量、错误、延迟、实例、版本、最近发布 | 值守 / 开发 |
| 依赖与资源 | JVM、MySQL、Redis、磁盘、任务 | 开发 / 运维 |
| 业务质量 | 登录、权限异常、工单流转、通知、附件 | 产品 / 开发 / 值守 |

看板标注环境、时区、单位和数据刷新延迟，并叠加发布 / 迁移时间点，便于判断变化相关性。

## 9. 告警策略

### 9.1 原则

- 告警必须可行动：有影响、负责人、排查入口和恢复判定。
- 使用持续窗口和去重，避免单个瞬时点造成噪声。
- 同一根因尽量聚合；依赖故障不应触发几十条等价应用告警。
- 阈值先基于测试和历史基线设置，再按实际流量调整；文档中的示例不是生产默认值。

### 9.2 初始分级

| 级别 | 场景 | 响应 |
| --- | --- | --- |
| SEV-1 | 广泛不可用、数据破坏、越权或敏感信息泄露 | 立即响应，停止发布 / 写入，通知安全与负责人 |
| SEV-2 | 核心功能显著失败、错误率或延迟持续超标 | 值守立即处理，评估回滚 |
| SEV-3 | 局部降级、任务连续失败、容量接近阈值 | 工作时段处理并跟踪期限 |
| SEV-4 | 趋势、单次非关键失败或维护提醒 | 进入待办和容量计划 |

### 9.3 首批规则候选

- 多实例 readiness 持续失败或可用实例不足。
- 核心 route 的 5xx 比例在有最小请求量时持续超阈值。
- 登录失败异常突增，区分攻击、配置问题和正常密码错误。
- 数据库连接池等待 / 耗尽，Redis 超时持续升高。
- 任务连续失败，通知 / 附件补偿积压。
- 日志或上传卷空间接近上限。
- 发布后关键指标相对发布前基线显著恶化。

每条规则必须链接到 runbook，并记录 owner、静默条件和最近一次演练日期。

## 10. 事件处理流程

```text
告警 / 用户报告
  → 确认环境、影响和时间窗
  → 指定事件负责人并建立时间线
  → 关联最近发布 / 迁移 / 配置
  → 通过指标缩小范围、用 request ID 查日志
  → 缓解：隔离、降级、停止任务、回滚
  → 验证恢复并持续观察
  → 复盘与修复跟踪
```

事件中优先恢复安全和关键能力，保全日志、故障库和发布证据。禁止在未记录前直接清库、删日志或覆盖故障制品。

## 11. Runbook 模板

```markdown
# <告警 / 故障名称>

## 影响与入口
- 用户影响：
- 对应告警 / 看板 / 日志查询：
- owner 与升级联系人：

## 首查
1. 确认环境、版本、最近发布和事件起点。
2. 检查健康、错误率、延迟和关键依赖。
3. 使用 request ID 查看脱敏日志。

## 缓解
- 可逆操作、授权要求、预期效果和停止条件。

## 回滚 / 恢复
- 对应发布 runbook、数据和附件注意事项。

## 恢复验证
- 健康、冒烟、指标恢复范围和观察时间。

## 记录
- 时间线、操作者、证据、根因、后续负责人和期限。
```

命令必须包含明确环境和目标，不依赖当前目录或未展开变量。破坏性操作单独标注审批与恢复点。

## 12. 常见场景首查

| 场景 | 先看 | 再看 |
| --- | --- | --- |
| 登录普遍失败 | 登录失败率、Redis、版本 / secret 变更 | request ID 日志、时钟、验证码依赖 |
| API 5xx | route 错误率、最近发布 | 异常类型、MySQL / Redis、连接池 |
| 页面慢 | API P95、静态资源 / 代理 | SQL、连接池、JVM GC、浏览器网络 |
| 定时任务失败 | 任务日志、连续失败数 | invoke target、依赖、并发和执行时长 |
| 上传失败 | 目录容量 / 权限、请求大小 | 文件类型校验、元数据事务、Nginx 限制 |
| 权限异常 | 401 / 403 分布、角色 / 菜单变更 | LoginUser、方法权限、DataScope、审计日志 |

## 13. 保留、访问与成本

- 登录、操作和安全审计日志的保留期由合规 / 业务要求确定，普通 debug 日志更短。
- 日志和指标系统使用最小权限，查询敏感审计记录需留痕。
- 轮转、压缩和容量告警防止日志占满磁盘。
- 高流量接口采用合理采样，但错误和安全事件不得被无规则丢弃。
- 删除到期数据时保留删除策略和执行记录，不通过手工临时清理维持容量。

## 14. 验证清单

- [ ] 成功、4xx 和 5xx 请求能用 request ID 串联入口与后端。
- [ ] 日志抽样不含密码、Token、Cookie、secret、敏感正文和物理附件路径。
- [ ] liveness / readiness 在 MySQL、Redis 和迁移异常下符合设计。
- [ ] 指标有单位、环境、版本和规范化 route，不含高基数敏感标签。
- [ ] 每条阻断级告警都有 owner、持续窗口、runbook 和恢复条件。
- [ ] 发布标记能与错误、延迟、资源和业务指标关联。
- [ ] 至少演练一次依赖不可用、应用回滚和磁盘容量告警。
- [ ] 事件记录包含影响、时间线、决策、证据和后续负责人。
