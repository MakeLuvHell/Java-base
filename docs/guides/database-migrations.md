# 数据库迁移规范

本文定义数据库结构、基础数据、菜单和字典的版本化交付方式。

> **当前基线（2026-08-03）：** 仓库只有 `sql/ry_20260417.sql` 与 `sql/quartz.sql`，没有 `sql/migrations/`、迁移 runner、版本台账或自动迁移验证。
> **目标状态：** W8 起按版本提交正向 / 回滚脚本，W11 由 CI 验证空库和旧基线升级，W12 将迁移设为发布硬门禁。
> **生效边界：** 在迁移工具正式落地前，本规范是目标约定；脚本只能在明确的本地 / 隔离测试库中按评审步骤执行。

相关：[研发协作流程](./development-workflow.md) · [测试策略](./testing-strategy.md) · [发布与回滚](./deployment-and-rollback.md) · [W8 任务书](../intern/tasks/W8-ticket-center-mvp.md)

## 1. 基本原则

1. **数据库变化也是代码。** 脚本与使用它的代码在同一 PR 评审、测试和发布。
2. **已发布的正向脚本不可改写。** 发现问题时新增更高版本修复，不能静默修改校验值。
3. **先兼容，再清理。** 生产演进优先使用 expand / migrate / contract，避免一次发布同时破坏新旧版本。
4. **执行环境必须明确。** 每次执行前打印并人工确认环境、主机、库名、当前版本和备份点。
5. **失败即停止。** 任一版本失败后不得跳过继续启动新应用。
6. **回滚要按数据风险决定。** 共享环境优先应用回退 + 前滚修复；破坏性 U 脚本或恢复备份必须单独审批。

## 2. 目录与命名

目标目录：

```text
sql/
├── ry_20260417.sql
├── quartz.sql
└── migrations/
    ├── README.md
    ├── V001__ticket_mvp.sql
    ├── U001__ticket_mvp.sql
    ├── V002__ticket_workflow.sql
    └── U002__ticket_workflow.sql
```

命名规则：

| 部分 | 规则 | 示例 |
| --- | --- | --- |
| 方向 | `V` 为正向，`U` 为对应回滚 | `V003` / `U003` |
| 版本 | 三位、全局递增、合并前不得重复 | `001`、`002`、`003` |
| 分隔 | 两个下划线 | `V003__...` |
| 描述 | 小写 snake_case，只写本次增量 | `ticket_attachment_notification` |
| 编码 | UTF-8，LF，文件末尾换行 | 不带 BOM |

版本号由目标分支全局顺序决定。多个并行 PR 冲突时，后合并者重编号并重新验证。不要用日期或个人编号绕开冲突，也不要使用 `MAX(version) + 1` 在运行时生成版本。

## 3. 每个脚本必须包含什么

文件头至少说明：

```sql
-- Version: V001
-- Purpose: ticket MVP schema, dictionaries and permissions
-- Applies to: local/test until the migration runner is approved
-- Depends on: baseline sql/ry_20260417.sql
-- Rollback: U001__ticket_mvp.sql
-- Data impact: describe backfill, deletion or compatibility risk
```

正向脚本按依赖顺序组织：

1. 新表 / 列 / 约束。
2. 索引。
3. 必要的数据回填。
4. 字典类型与字典项。
5. 菜单、按钮权限和角色关联。
6. 验证查询（只读，或放在同版本说明中）。

对应 U 脚本以逆依赖顺序撤销且只能处理本版本新增内容。U002 不得删除 V001 的对象，U003 也不得清理 W8 / W9 数据。

## 4. DDL 与数据变更规则

### 4.1 表和字段

- 表、列、索引和约束名称清晰且稳定，显式指定字符集 / 排序规则时与现有库保持一致。
- 新的必填列先允许空值或提供兼容默认值，完成回填和验证后再收紧。
- 删除 / 重命名列采用两阶段：先让应用停止读写，再在后续版本删除。
- 大表 DDL 需评估锁表时间、磁盘空间和数据库版本能力，并在隔离数据集测量。
- 外键、唯一约束和索引必须说明要保护的业务规则，不能只为“以后可能用到”而添加。

### 4.2 DML 和回填

- 回填需限定目标范围，记录预计 / 实际行数；禁止无 `WHERE` 的更新或删除，除非设计明确且双人复核。
- 大批量回填分批执行，定义批大小、可恢复位置和并发写入策略。
- 业务时间、创建人等字段使用明确规则，不能伪造真实用户操作记录。
- 脚本不得包含真实用户、生产数据、明文口令、Token 或 secret。

### 4.3 MySQL 事务限制

MySQL 的部分 DDL 会隐式提交，不能把“放在事务中”当作完整回滚保证。设计时分别处理：

- DDL 已成功、DML 失败。
- 表已建、索引失败。
- 回填执行一半。
- 应用已回退但新数据仍使用新结构。

每个高风险步骤都要有可重入或人工恢复说明，并在 runner 台账中记录真实完成状态。

## 5. 菜单、字典与基础数据

### 5.1 菜单和权限

- 目录、页面和按钮权限一起评审，权限字符需与后端 `@PreAuthorize`、前端指令一致。
- 合并前检查 `menu_id`、路由 path、component 和 `perms` 是否冲突。
- 固定 ID 只能使用团队已分配且验证空闲的区间；禁止通过 `MAX(menu_id) + 1` 生成关联 ID。
- 插入角色菜单关联前先解析并验证目标菜单；回滚只删除本版本创建的关联和菜单。
- 删除顺序通常为角色关联 → 按钮 → 页面 → 目录，不能留下悬挂引用。

### 5.2 字典

- `dict_type` 是稳定业务键，创建前检查是否已存在及语义是否一致。
- 字典值是持久化契约，显示文案可以调整，但不能无迁移地改变已有值的含义。
- 回滚前检查是否已有业务行引用该字典值；有数据时优先停用，不能直接删除。
- Java / SQL / 前端对状态值的定义必须一致，状态机规则不得只依赖显示文案。

## 6. 迁移 runner 与版本台账

首次落地时选择成熟迁移工具（如与当前 Spring Boot / MySQL 版本兼容的 Flyway）或经架构评审的等价方案，不自行拼接一个缺少锁、校验和失败恢复的 shell runner。

runner 最低能力：

- 按版本严格排序，每个版本只成功执行一次。
- 记录版本、描述、文件校验值、执行时间、结果和执行主体。
- 对已应用脚本的校验值变化立即失败。
- 多实例发布时有迁移锁，避免并发执行。
- 失败版本可定位且不会被自动标记成功。
- 使用独立最小权限账号；运行时应用账号不应拥有任意 DDL 权限。

若选定工具不原生执行 U 脚本，U 文件仍可作为经过评审的恢复材料，但不得伪装成自动回滚能力。工具、目录、版本格式一旦确定，应同步修改本文和 `sql/migrations/README.md`。

## 7. 两条强制验证路径

### 7.1 干净数据库

```text
创建明确命名的空测试库
  → 导入当前基线初始化脚本
  → 按顺序执行全部 V 脚本
  → 启动目标应用
  → 执行结构、字典、菜单、权限和核心业务冒烟
```

验证：所有对象只出现一次，版本台账完整，应用可启动，菜单和按钮与权限契约一致。

### 7.2 旧版本快照

```text
恢复已脱敏的上一发布版本快照
  → 记录起始版本和关键行数
  → 执行待发布 V 脚本
  → 验证回填、约束、兼容读写
  → 启动新应用并执行回归
```

只测空库无法发现真实旧数据导致的唯一约束、空值、长度和状态冲突。

### 7.3 失败与恢复演练

- 在隔离库制造一个中途失败，确认 runner 停止且应用不会越过门禁。
- 验证 U 脚本或前滚修复只影响目标版本。
- 对破坏性版本，从备份恢复到另一实例并核对结构和关键业务计数。
- 再次运行迁移时，已成功版本应被台账跳过而非重复执行 DML。

## 8. 发布兼容策略

推荐三阶段：

| 阶段 | 数据库 | 应用 |
| --- | --- | --- |
| Expand | 新增兼容列 / 表 / 索引 | 旧版本仍可运行 |
| Migrate | 回填并验证数据 | 新版本双读 / 双写或使用新结构 |
| Contract | 后续版本删除旧结构 | 确认无旧实例和旧任务依赖 |

发布前明确兼容窗口。若新旧应用无法同时使用当前数据库，必须安排停写窗口和完整恢复点，不能做滚动发布。

## 9. 回滚决策

| 情况 | 优先动作 | 数据处理 |
| --- | --- | --- |
| 应用错误，数据库向后兼容 | 回退应用制品 | 保留已应用迁移 |
| 新迁移有缺陷但未产生业务数据 | 停止发布，评审 U 或修复 V | 在隔离验证后执行 |
| 已产生不可逆新数据 | 停写并评估前滚修复 | 不直接执行破坏性 U |
| 结构 / 数据严重损坏 | 隔离故障库，恢复到新实例 | 按恢复点核对后切换 |

U 脚本不是默认生产按钮。涉及删表、删列、删除字典或回退数据时，必须说明数据损失、停止写入条件、备份和验证负责人。

## 10. 环境安全

执行前逐项确认：

- [ ] 环境名、数据库主机、端口、库名和账号均为明确值。
- [ ] 不是生产环境；若为授权发布，已有变更单、双人确认和恢复点。
- [ ] 备份已完成并在独立实例验证可恢复。
- [ ] 当前 schema / 版本 / 校验值符合预期。
- [ ] 连接账号权限满足最小化，不使用应用中的示例凭据。
- [ ] 命令没有未展开变量、宽泛通配符或会误选其他库的默认值。
- [ ] 日志不会打印口令、连接串 secret 或真实业务数据。

## 11. PR 交付清单

- [ ] V / U 版本成对、命名正确、依赖范围清楚。
- [ ] 正向和回滚脚本没有修改已发布版本。
- [ ] 表、索引、约束、菜单、字典与代码契约一致。
- [ ] 空库与旧快照两条路径均有命令和结果。
- [ ] 回填行数、耗时、失败恢复和兼容窗口已记录。
- [ ] 回滚不会误删早期版本或用户数据；不可逆项已明确。
- [ ] 发布门禁、备份和恢复方案已同步到发布文档。
