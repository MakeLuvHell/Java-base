## 0. 本周交付结果

工单参与者可以上传和下载附件；被分派、收到评论、工单解决或重开时，相关用户收到站内通知；通知支持已读/未读；工单详情时间线能追踪流转、评论和附件事件。

这一周的核心问题不是“上传成功”，而是：

- 谁可以上传、查看、下载和删除。
- 文件元数据与磁盘文件如何保持一致。
- 数据库事务提交失败时不能留下垃圾文件或虚假通知。
- 通知失败不能回滚已经成功的核心工单流转。
- 前端不能通过可猜测的 `/profile/**` 地址绕过鉴权。

### 本周明确不做

| 不做 | 原因 |
| --- | --- |
| 将附件直接暴露为公共静态 URL | 与 SEC-009 相冲突 |
| 邮件、短信、第三方 IM | 先完成站内可靠闭环 |
| WebSocket 在线推送 | 未读轮询/刷新已足够验证业务 |
| 大文件分片、断点续传、对象存储 | 本周只做受控小附件 |
| 把通知塞进广播公告表 | 工单通知有明确接收人和业务引用，应独立建模 |

## 1. 默认业务规则

### 1.1 附件

| 规则 | 默认值 |
| --- | --- |
| 单文件大小 | 不超过 10 MB，且不高于系统 multipart 限制 |
| 单工单数量 | 最多 10 个未删除附件 |
| 允许类型 | png/jpg/jpeg/pdf/txt/docx/xlsx；导师可裁剪 |
| 文件名 | 保存原始展示名；磁盘名由服务端随机生成 |
| 上传人 | 工单创建人、当前处理人、工单管理员 |
| 下载人 | 有查询权限且属于可见数据范围的工单参与者/管理员 |
| 删除人 | 上传人；工单管理员可删除，必须记录原因 |
| 终态 | CLOSED/REJECTED 默认只能下载，不能再上传或删除 |

只检查扩展名不够；需要复用项目已有上传工具的文件名、路径和 MIME 基础校验。原始文件名不能参与磁盘路径拼接。

### 1.2 通知接收人

| 事件 | 接收人 |
| --- | --- |
| ASSIGN/TRANSFER | 新处理人 |
| COMMENT | 创建人和当前处理人，排除操作者本人 |
| RESOLVE | 创建人 |
| REOPEN | 当前处理人 |
| CLOSE/REJECT | 创建人和当前处理人，排除操作者本人 |

同一事件、同一接收人只能生成一条通知。通知内容保存必要快照，但前端跳转以 `ticket_id` 为准。

### 1.3 已读规则

- 用户只能读取和修改自己的通知。
- 支持单条已读和当前用户全部已读。
- 未读数按当前登录用户实时查询或短时缓存；若使用缓存，必须定义失效点。
- 工单被删除或用户失去数据范围后，点击旧通知不能泄露工单详情。

## 2. 数据模型

### 2.1 附件表 `biz_ticket_attachment`

| 字段 | 说明 |
| --- | --- |
| `attachment_id` | 主键 |
| `ticket_id` | 工单 ID，索引 |
| `original_name` | 展示文件名 |
| `storage_name/storage_path` | 服务端内部存储信息，不直接返回绝对路径 |
| `file_size/content_type/extension` | 校验和展示信息 |
| `storage_status` | `PENDING/READY/FAILED`；只有 READY 可列表和下载 |
| `cleanup_status/cleanup_error` | 物理清理状态与截断后的失败原因，供重试和审计 |
| `uploader_id/create_by/create_time` | 上传人快照 |
| `del_flag` | 逻辑删除 |

### 2.2 通知表 `biz_ticket_notification`

| 字段 | 说明 |
| --- | --- |
| `notification_id` | 主键 |
| `event_id` | 业务事件 ID，用于幂等 |
| `ticket_id` | 工单 ID |
| `receiver_id` | 接收用户 ID，建立联合索引 |
| `event_type/title/content` | 通知快照 |
| `read_flag/read_time` | 未读/已读 |
| `create_time` | 创建时间 |

唯一约束：`uk_event_receiver(event_id, receiver_id)`。

### 2.3 审计事件

复用 W9 的时间线 DTO，将附件上传/删除和通知触发所对应的业务动作加入统一时间线。不要把“用户阅读通知”显示为工单业务时间线事件。

### 2.4 SQL 交付

```text
sql/migrations/V003__ticket_attachment_notification.sql
sql/migrations/U003__ticket_attachment_notification.sql
```

U003 只能回滚 W10 新增表、权限和索引，不能删除磁盘文件；回滚前必须说明如何备份/清理测试附件。

## 3. 接口与权限契约

### 3.1 附件

| 能力 | 方法与路径 | 权限字符 |
| --- | --- | --- |
| 附件列表 | `GET /ticket/ticket/{id}/attachments` | `ticket:attachment:list` |
| 上传 | `POST /ticket/ticket/{id}/attachments` | `ticket:attachment:upload` |
| 下载 | `GET /ticket/attachment/{attachmentId}/download` | `ticket:attachment:download` |
| 删除 | `DELETE /ticket/attachment/{attachmentId}` | `ticket:attachment:remove` |

下载接口按附件 ID 查询元数据，再校验工单可见性和参与者身份，最后输出文件流。响应不得暴露服务器绝对路径。

### 3.2 通知

| 能力 | 方法与路径 | 权限字符 |
| --- | --- | --- |
| 我的通知 | `GET /ticket/notification/list` | 登录即可；只查本人 |
| 未读数 | `GET /ticket/notification/unread-count` | 登录即可；只查本人 |
| 单条已读 | `PUT /ticket/notification/{id}/read` | 登录即可；只改本人 |
| 全部已读 | `PUT /ticket/notification/read-all` | 登录即可；只改本人 |

是否设置独立菜单权限由导师决定；无论是否设置，Service/Mapper 都必须强制 `receiver_id = 当前用户`。

### 3.3 返回模型

- 附件 DTO 只返回 ID、原始名、大小、类型、上传人和时间，以及当前用户可执行动作。
- 通知 DTO 返回业务摘要、readFlag、时间和受控前端路由参数。
- 文件不存在、元数据不存在、无权限分别给出可区分但不泄露内部路径的错误。

## 4. 一致性与副作用设计

### 4.1 上传顺序

默认流程：

```text
校验工单和权限
  → 校验数量/大小/扩展名
  → 写入临时文件
  → 数据库保存 PENDING 元数据
  → 事务提交后移动到最终位置
  → 新事务标记 READY 并记录时间线事件
```

移动或最终状态更新失败时标记 `FAILED`，普通列表/下载不能暴露该附件，并提供幂等的清理或重试方法。进程在任一步中断后，能够根据 `storage_status` 和临时文件年龄进行恢复。也可以先写最终文件再补偿删除，但设计文档必须说明数据库失败、补偿删除失败和进程中断时如何收敛。禁止没有状态字段或补偿策略的“先落盘再随缘写库”。

### 4.2 删除顺序

- 先做权限与终态校验。
- 数据库逻辑删除和时间线记录在事务内完成。
- 物理文件删除在提交后执行；失败进入可重试清理记录或明确告警。
- 不能因为磁盘删除失败而恢复一个已经对用户不可见的附件。

### 4.3 通知触发

工单核心事务提交成功后再创建通知。建议使用 Spring 事务事件或等价的提交后机制；通知写入失败不能回滚已成功的工单状态流转。

最小可恢复方案必须同时具备：

1. W9 流转记录、评论 ID 或附件时间线 ID 作为持久化 `eventId`；不能只依赖内存事件。
2. 一个按 `eventId` 重新加载源事件并重算接收人的幂等 `deliver(eventId)` 方法。
3. 失败日志/指标包含 `eventId`、事件类型和失败阶段，但不含通知正文中的敏感内容。
4. 导师账号可调用的受权重试入口，或等价的定时扫描机制；重试仍由 `uk_event_receiver` 兜底去重。

若增加 HTTP 重试入口，权限使用 `ticket:notification:retry`，并记录操作日志；普通用户不能触发任意历史事件重放。

不要求本周引入消息队列。若使用异步线程，必须说明线程池、登录上下文不可直接复用和失败去向。

### 4.4 幂等

通知使用 W9 流转记录/评论产生的稳定 eventId，加数据库唯一约束。重试同一业务事件时不得产生重复通知。

## 5. 前端交互要求

### 5.1 工单详情附件区

- 上传按钮、文件选择、进度/提交状态。
- 文件名、大小、上传人、时间、下载和删除动作。
- 超限、类型不支持、无权限和文件丢失提示。
- 长文件名可查看完整内容，不能撑破布局。
- 下载使用鉴权请求和 Blob，禁止拼接 `/profile/...` 打开。

### 5.2 通知中心

- 顶部入口显示未读数，0 时不显示空徽标。
- 列表支持全部/未读筛选、分页、单条已读和全部已读。
- 点击通知前先标记已读，再跳转工单详情；详情无权访问时显示明确结果。
- loading、empty、error、submitting 状态尺寸稳定。
- 前端路由参数只包含业务 ID，不包含磁盘路径或敏感内部字段。

### 5.3 时间线

附件上传/删除应与流转、评论使用统一时间线样式；不同事件用图标和文案区分，不能只靠颜色。

## 8. 必测矩阵

| 场景 | 预期 |
| --- | --- |
| 参与者上传合法 PDF | 元数据与文件均存在，时间线有一条事件 |
| 上传超限/非法扩展名 | 拒绝，数据库和磁盘无残留 |
| 原始名包含 `../` | 不影响真实存储路径 |
| 非参与者猜 attachmentId 下载 | 拒绝，不返回绝对路径 |
| 已删除附件下载 | 拒绝 |
| 元数据存在但文件丢失 | 稳定错误并记录日志，不返回空 200 |
| 删除文件物理清理失败 | 业务侧不可见，有可追踪的清理失败 |
| 工单分派 | 新处理人恰好收到一条未读通知 |
| 重放相同 eventId | 不新增重复通知 |
| 操作者给自己触发事件 | 不生成自通知 |
| A 读取/已读 B 的通知 | 拒绝且 B 的 readFlag 不变 |
| 失去工单数据范围后点旧通知 | 不能查看工单详情 |
| 通知写入失败 | 工单流转仍提交，失败有记录/重试入口 |
| 普通用户重放历史通知事件 | 403；不能借重试接口向任意用户制造通知 |
| 导师账号重试同一失败 eventId 两次 | 最终每个接收人只有一条通知 |
| U003 回滚 | W8/W9 工单与流转仍可使用 |

## 9. 验收标准

- [ ] 附件上传、列表、鉴权下载和删除形成闭环。
- [ ] 附件不通过匿名 `/profile/**` URL 暴露。
- [ ] 路径、扩展名、大小、数量和参与者权限均由后端校验。
- [ ] 数据库失败和文件失败都有明确补偿/收敛策略。
- [ ] `PENDING/FAILED` 附件不会被普通列表或下载暴露，重试/清理操作幂等。
- [ ] 通知在核心事务提交后触发，失败不回滚工单流转。
- [ ] eventId + 唯一约束阻止重复通知。
- [ ] 通知失败能从持久化源事件按 eventId 受权重试，而不是只能翻日志后手工补库。
- [ ] 用户只能读写自己的通知。
- [ ] 未读入口、通知列表、附件区和统一时间线状态完整。
- [ ] 安全测试使用非管理员账号和直接接口请求完成。
- [ ] V003/U003、构建、自测和清理步骤有真实记录。

## 11. 常见坑与求助

| 坑 | 修正方向 |
| --- | --- |
| 下载地址直接使用 `/profile/...` | 改为附件 ID + 鉴权流式下载 |
| 事务回滚但磁盘留下文件 | 使用临时文件/提交后移动或补偿删除 |
| 通知异常导致工单操作失败 | 将通知放到提交后副作用并记录失败 |
| 同一事件出现多条通知 | 稳定 eventId + receiver 唯一约束 |
| 全部已读误改他人通知 | 更新条件必须带当前 receiverId |
| 删除附件后审计记录消失 | 时间线保存必要快照，不依赖已删元数据展示 |

求助时附：当前用户和工单身份、附件/通知 ID、请求响应、文件元数据、磁盘相对路径、事务阶段、事件 ID、错误日志首段和已尝试的补偿步骤。
